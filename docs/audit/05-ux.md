**Date:** 2026-08-21 · **Base:** `ce8e729` (main, after the deferred items closed)

## Findings

### H1 — High: the invariant suite was red, and it was my fault

`npm run test:invariants` is this repo's design-rule guard: 300-plus
assertions about how the product must look and behave. It exits non-zero on
any failure, so a red suite means **no rule in it is being enforced** —
a genuine regression would land in exactly the same red output as the
expected noise and nobody would see it.

It was failing **5** tests. The previous round's fix log recorded "2
pre-existing failures" as acceptable background, which is how this
degrades: once a suite is allowed to be red, each new failure hides in the
noise.

All five traced back to earlier passes in this same audit:

| Failing invariant | Rule it still encoded | Why it changed |
|---|---|---|
| `power animals each keep their own color` | every animal gets a unique colour | Pass 1: ten theme animals now take *their theme's* colour so the card and the allocation slice match; eleven are graded by temperament |
| `chrome is quiet…` | active segment paints `bg-background` | Pass 1: an opaque fill on a translucent card swallowed what sat under it — the "default gray gets eaten by the highlight" report |
| `workspace nav marks the current room…` | active room is `bg-primary text-primary-foreground` | Pass 1: marking where you are is not an action, so it stopped wearing the CTA fill |
| `legal pages name the operator…` | a standalone "I am {minAge} or older" checkbox | Martin's request: fold age into the Terms/Privacy consent line |
| `fund cron posts to X…` | gate on `xPostingConfigured` | Martin's request: never post unless explicitly switched on |

**Four of the five encode changes Martin explicitly asked for.** The code
was right and the tests were stale. That distinction matters for the fix:
the answer is never to revert the code to satisfy an old assertion, and it
is also never to weaken the assertion until it passes.

*Severity:* **High.** Not because any user-visible thing is broken — none
is — but because the mechanism that would catch a user-visible regression
was switched off, silently, for five separate design rules.

### H2 — High: the watchlist box fails silently, four different ways

*File:* `src/components/WatchlistStrip.tsx`

`add()` had four paths out, and every one of them was a bare `return`:

```ts
if (!/^[A-Z0-9.=^-]{1,12}$/.test(t)) return;   // could not resolve a name
if (heldTickers.some((h) => h.toUpperCase() === t)) return;  // you own it
// ...and a search fetch that throws lands in the first case
// ...and a duplicate was added again with no acknowledgement
```

The whole component contains **no error state, no toast, and no `catch`
that reports anything**:

```
$ grep -cE "toast|setErr|setError|Alert" src/components/WatchlistStrip.tsx
0
```

So: you type a company name, press Enter, and the app does nothing at all.
No message, no spinner, your text still sitting in the box. From the
outside that is indistinguishable from the app being broken — and the
"you already own this" case is worse than a plain failure, because the
reason is a perfectly good one that the person is simply never told.

There is also no pending state on the one slow path. Turning a typed
company name into a ticker costs a network round trip; on a slow
connection the box sits inert for its duration.

**What makes this a clear defect rather than a judgement call:** the
onboarding modal ten files away implements the *same interaction* — type a
ticker or company name, press Enter — and gets every one of these right,
with `setStockError("Type a ticker or a company name.")`, `stockBusy`, and
a distinct message for each failure. The standard already exists in the
codebase; this component just does not meet it.

### M1 — Medium: options gating contradicted AGENTS.md (now decided)

*File:* `src/lib/experience-tier.ts:101`

```ts
export function shouldHideOptions(knowsOptions: boolean | null): boolean {
  void knowsOptions;
  return false;
}
```

`AGENTS.md` states the rule as live product policy:

> Use `shouldHideOptions()`: options/covered-call UI is shown **only when
> `knows_options === true`**. Unanswered and "no" both hide it.

The code does the opposite: it ignores the answer and shows options UI to
everyone. The function's own comment explains why — a deliberate product
call on 2026-08-18 to disable the gating "until this is fully thought
through", with instructions for restoring it.

So this is not a bug; it is **a documented decision and a governing
document that now disagree with each other.** One of the two is out of
date, and only Martin knows which.

The user-facing consequence, stated plainly so the decision can be made on
it: someone who answered "no, I don't know options" during onboarding is
currently shown covered-call panels, strike alerts and Call % fields — in a
product whose stated principle is that a grandma should understand every
sentence.

**Decided (Martin delegated the call): hide on an explicit "no" only.**

`shouldHideOptions` now returns `knowsOptions === false`. Neither of the two
literal readings was right, and the reason is structural rather than a
matter of taste:

```ts
export function shouldSkipExperienceOnboarding(input: {...}): boolean {
  if (input.holdingsCount > 0) return true;   // <- this line decides it
  ...
}
```

**Anyone who already owns anything never sees the question**, so their
`knows_options` is permanently `null`. Implementing AGENTS.md literally —
`knowsOptions !== true`, where unanswered also hides — would therefore have
stripped covered calls from *every existing holder at once*: people who had
been using the feature for months, who were never asked, and who would have
had no idea why it vanished. That is not the safety posture the rule was
reaching for; it is an outage wearing its clothes.

Hiding on an explicit "no" keeps the protection exactly where it was aimed
— someone who told us they don't know options doesn't get options machinery
— and leaves everyone else as they were. The answer is changeable both ways
in Account (`AccountPage.tsx:228`), so a `null` is not a dead end.

`AGENTS.md` was updated to match, with the reasoning recorded inline. That
matters more than the code change: **the finding here was that the governing
document and the code disagreed**, and fixing only one side would have
regenerated this finding on the next pass.

Pinned by `src/lib/experience-tier.test.ts`, including a test that ties the
`null` case to `shouldSkipExperienceOnboarding` directly, so the reasoning
cannot rot apart from the rule it justifies.
